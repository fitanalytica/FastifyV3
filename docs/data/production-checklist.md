# Before production

Everything that must be done, run or decided before v3 goes live. **Keep this list current**: add a line when a change needs something outside the code (a schema change, a script, a setting, a clean-up), and tick it when it is done on production. Status: `[ ]` to do, `[x]` done on production.

## 1. Database (Postgres)

Run the scripts in `dev-db/` **in order** on production, with the same statements; each was written for it (`CONCURRENTLY` indexes run **outside a transaction**, constraints are added `NOT VALID` and then validated). Take a backup first.

- [ ] **Check the real data first** ([schema.pg.md](schema.pg.md) section 8, "What the real data shows"): the counts of `tosend` and `iswatch` (old watch rows left at `tosend = 2` would flood the inbox), and the second check listed there.
- [ ] `04-migration-v3.sql`: the new `activities` columns and the `tosend` check, the three activity indexes, `userinfo.geo_source` and **`geom` made nullable**, the `walkdata` columns and index, `usertokens` (**one row per device**: drops `unique_applegoogle_device`; adds `prev_refresh_token` and `prev_changed_date` for the refresh grace, and its index). The "housekeeping drops" it leaves out come last, after the app is live.
- [ ] `05-feed-v3.sql`: `activities.route_preview` and the `activities_feed` index.
- [ ] `06-posts-v3.sql`: the `posts` table and its two indexes.
- [ ] `07-account-deletion-v3.sql`: the `account_deletion_codes` table (the e-mailed code for deleting an account).
- **Do NOT run `08-billing-standin.sql` on production**: it is a local stand-in for the old app's `paymentstore`, which production already has.
- [ ] **Subscriptions and deleting an account (a rule to keep):** a user who has bought a subscription keeps their `userinfo` row (billing needs it); everything else of theirs is deleted. The test is a row in `paymentstore` for the user. **Before the deletion goes live, check on production:** (1) the foreign keys of `paymentstore`, `validatereceiptstore` and the other billing tables: if one points at `userlogin` with `ON DELETE CASCADE`, deleting the login **deletes the billing rows too**: change it (to `SET NULL` or no action, or copy what billing needs first); (2) which tables really count as "bought": only `paymentstore` (Android) is tested today, but iOS buyers are in `payments` and every buyer has a `membership` row (plus the `_sandbox` copies), so the test must cover those too, and note that deleting the login **cascades** to `protection_logs`, `streak_logs` and `paymenterrors` (a streak buyer's purchase ledger would go); (3) whether a kept row should lose more personal data (`about`, `fname`, `lname`, the place) after the period billing must keep it: the picture and cover are cleared already.
- [ ] Account deletion also needs `quotations` (the old table whose key blocks deleting a login) to be handled where it exists: it is deleted first, inside the transaction.
- [ ] `usertokens.deviceid` is set by the app (`DeviceInfo.getUniqueId()`) instead of generated: check the login code writes it ([schema.pg.md](schema.pg.md) section 4).
- [ ] Anything added after this was written goes here too (a new `dev-db/NN-*.sql`, **and** `reset.sh`).

## 3. Server settings (environment, never committed)

- [ ] `DEV_LOGIN` must be **false** (or unset) on production: `POST /auth/dev-login` answers like an unknown route only then.
- [ ] `REFRESH_GRACE_SECONDS` **unset** (30 days). It is `120` in local `.env.local` only, for testing.
- [ ] S3: only `S3_REGION`, signed with the server's role. No `S3_ENDPOINT`, no MinIO keys. The buckets (`activitees` for media, `fitpy` for profile images) and their CORS and lifecycle rules.
- [ ] Weather: **real** `WEATHER_API` and `OPEN_WEATHER_API` keys. The ones used locally are **test keys**: replace them, and never put keys in a file that is committed. Without both, `POST /weather` answers 503 and finished activities are held back from the feed ([phone.md](phone.md) section 3b).
- [ ] **Sign in with Apple and Google** (built): `APPLE_CLIENT_ID` (`com.fitanalytica`; the audience of Apple's tokens), `APPLE_TEAM_ID`, `APPLE_KEY_ID` (or `APPLE_SIGNIN_KEYID`) and the Sign in with Apple Key's `.p8` as `APPLE_SIGNIN_PRIVATE_KEY_BASE64` (or `APPLE_PRIVATE_KEY_PATH`, or the PEM in `APPLE_PRIVATE_KEY`; kept out of git; **not** the `APPLE_IAP_*` subscription key) **are needed to keep Apple's refresh token (and so to revoke it)**; without them login still works but nothing can be revoked. `GOOGLE_CLIENT_IDS` (comma-separated: the iOS OAuth client, and the web client if one is used) is **required** or Google login answers 503. Optional: `LOGIN_RATE_LIMIT` (default 20 tries a minute per address).
- [ ] Apple Developer: the "Sign in with Apple" capability on the App ID `com.fitanalytica` and a Key for it. Google Cloud: the iOS OAuth client of the app (its reversed id is already the URL scheme in `Info.plist`) and the consent screen **published** (not in testing, which limits users).
- [ ] **E-mail (the deletion code):** `SNS_ARN` (the topic the old API publishes mail to) and `SNS_REGION` (us-east-1), and the server's role with `sns:Publish` on it. Locally, put the topic in `.env.local` **and** AWS credentials in the environment (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`); without `SNS_ARN` and with `DEV_LOGIN=true` the code is only written to the server's log. The consumer of the topic must send `body` as plain text.
- [ ] The server's role needs `s3:ListBucket` and `s3:DeleteObject` on **both** buckets (`activitees` and `fitpy`) for the account deletion (it lists each activity's and post's folder, then deletes).
- [ ] **The store catalogue** (`FastifyV3/src/services/store/catalogData.ts`): check every product id against both stores and the live payload, and fill `howItWorks` and `communication` (empty for now, the UI is being redone). A change to it is a deploy.
- [ ] `BILLING_ENV`: `production` (or unset) on the live server. Set it to `both` only if the same server must also serve TestFlight and App Review purchases (they are written to the `_sandbox` tables). Never set from the app.
- [ ] The database roles and connection strings (`PG_WRITER_URL`, `PG_READER_URL`, `PG_SSL`); the reader may lag the writer (the code reads the writer where it matters).

## 4. Code still to build

- [x] **Sign in with Apple and Google:** the login route (`POST /auth/login`) with token verification, Apple's token exchange (its refresh token is kept in `usertokens.apple_refresh_token`), the phone flows, logout through the server, a revoked Apple credential signs the user out, no picture is taken from Google. **Still to do on a real device** (section 5) **and with real keys.**
- [x] **Delete account** is built ([api.md](api.md) section 8b): the e-mailed code, every file of every activity and post and the pictures deleted from S3, Apple's grant revoked, every row deleted in one transaction. **To check on real systems:** a real e-mail through the topic (`SNS_ARN`), a real deletion with files in S3, and the Apple revoke with a real refresh token (section 5).
- [ ] **Subscriptions and in-app purchases in v3** ([api.md](api.md) section 15). **Built:** the Pro state, the catalogue, the bought protection days, and for **iOS** the purchase check (`POST /purchases/ios`) and the App Store notification (`POST /store/v3/appstore`), both through one grant function, with signatures checked. **Redeem is built** (atomic claim, 10 tries a minute per token). **Still to build:** Android (Google Play check and its Pub/Sub notification), taking back a refund or revoke (kept only). **Known problems in the old code, not carried over:** a millisecond `membership.expires_date` never read as ended (v3 reads both units; the old `subscriptionV3`, redeem and validate handlers still compare raw), the Android streak purchase writes a text order id into the bigint `protection_logs.transaction_id`, `isDev` chosen by the app, and the notification not checking the signature.
- [ ] **iOS purchases, before they can go live:** set `APPLE_APP_ID` (the numeric App Store id of the app: without it a production purchase answers 503); keep `certs/apple/*.cer` with the deploy (Apple's public roots, G3 and G2; check them against https://www.apple.com/certificateauthority/ now and then); in App Store Connect set the **server notification URL** (production and sandbox) to `https://<store host>/store/v3/appstore` when the old URL is switched over (the old one stays until then); make sure the **app puts the user's `store_id` as the `appAccountToken`** on every purchase (the notification finds the user by it when the phone never reported the purchase); and decide whether the notification route needs its own rate limit (the global limit is 100 a minute per address). `payments.convert_rate` is filled from the free currency list the old code uses (`cdn.jsdelivr.net/npm/@fawazahmed0/currency-api`): the server needs to reach it; if it cannot, the rate stored is 1 (as the old code did), which is wrong for any other currency: watch for it or fix such rows later. **Existing profiles with no `store_id`** are given one the first time their phone asks for its state; check on production how many users have none.
- [ ] **The phone's store, before it can go live** ([phone.md](phone.md) section 9c): **Associated Domains** `applinks:invite.fitanalytica.com` in the app's capabilities (and the `apple-app-site-association` file on that host listing the app and the path), so an invite link opens the app; the **In-App Purchase** capability; `react-native-iap` pods installed; test with a **sandbox Apple account** on a device (Xcode's local StoreKit test purchases are refused by the server). **Screens:** the Subscription sheet is built (with the gift-code list and How it works; those parts are not in Sketch yet: check them against a design). **Still to build:** the Pro card states in Settings, the protection packs, a pop-up for a purchase or a redeem (a toast until then), and a server call that records a code as shared (`membership.shared_date`; nothing sets it yet). **The Android flow:** Google Play purchases, the deferred invite link (Play Install Referrer). **The streak engine does not spend the bought protection days yet.**
- [ ] **Analytics** ([phone.md](phone.md) section 9d): in the GA4 property mark `purchase` and `sign_up` as **key events**, link the property to Google Ads, and register `pro`, `pro_source` and `auth_method` as **custom dimensions** (user scope) or they do not show in reports. Check the events once in **Firebase DebugView** (set `SEND_IN_DEV` in `src/services/analytics/index.ts`, run with `-FIRDebugEnabled`). **Consent is not asked yet:** `setTrackingConsent` exists but nothing calls it, and `CONSENT_REQUIRED` in `src/services/analytics/index.ts` is `false` (events go from the first launch): before release decide the consent screen (Europe) and, with ads, the iOS tracking prompt (`NSUserTrackingUsageDescription` and App Tracking Transparency). When ads are built, call `trackAdRevenue` from AdMob's paid event. Not yet tracked: Android purchases, notification clicks, voice coach use, ratings prompts, referral shares.
- [ ] **Crash reports** ([phone.md](phone.md) section 9e): check in the Crashlytics dashboard from a release build (or with `SEND_IN_DEV`) that a non-fatal arrives with its log line, the screen attributes and the account token as user id; check the **dSYM upload** for iOS symbolication; decide whether crash collection needs the user's consent (it does not carry personal data, but say so in the privacy policy). The error fallback screen has no Sketch design yet. Errors in `.catch` blocks are now reported (offline ones are not): watch the first release for noisy tags and move those to `info`.
- [ ] **Ads** ([phone.md](phone.md) section 9f, [api.md](api.md) section 15): the rules are `ADS_DATA` in `src/services/ads/adsData.ts` (every number is tuned there: grace, rollout, caps, cooldowns; `platforms` for one platform). **Review the starting values before the first release** (grace 1 day, gap 300 s, 3 a session, app open 4 a day with 2 h between, interstitial after an activity 3 a day with 1 h between, rollout 100, all inline slots off). **Built, not run on a device:** consent, the SDK and the full-screen ads. **To do on a real device:** run with the app id in `app.json` (`ca-app-pub-...~...`, iOS and Android) and `Info.plist` (`NSUserTrackingUsageDescription`, `SKAdNetworkItems`: both there); in AdMob set up the **privacy and messaging** (the European consent message and the iOS tracking (IDFA) message), or no form is shown; test with test devices; check that a release build uses the real units in `services/ads/unitIds.ts` and a debug build the test ones; check the interstitial after an activity and the app-open ad after the background (the first start shows none). **Not built yet:** the inline slots and native card (a design first).
- [ ] **A limit per user in the feed**, so one busy user cannot fill it ([server.md](server.md) the feed).
- [ ] **Compress the activity upload** (`POST /activities/batch` is not gzip-compressed yet).

- [ ] **Android:** Google Sign-In (an Android OAuth client with the app's SHA-1), Apple sign-in on Android (a Services ID and a web flow), the Kotlin port of the native engine ([native-engine.md](../native-engine.md)).
- [ ] **Rate-limit and abuse:** the login route is limited per address only; consider a limit per `sub` and monitoring of `LOGIN_REFUSED` in `apperrors`.
- [ ] Apple's **server-to-server notifications** (consent revoked, account deleted) as a webhook: optional.
- [ ] Profile editing sends name, about, gender, date of birth, height and weight; `timezone` and `hideprofile` are not part of `PUT /profile` (visibility has its own call).
